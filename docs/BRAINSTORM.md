# BRAINSTORM.md — Что не хватает в SMS Forwarder

> Анализ: что нужно приложению с точки зрения архитектуры и удобства пользователя.
> **Процесс для каждой идеи:** ветка → issue на GitHub → MR → CI → ревью → мерж.

---

## 🔄 Процесс реализации

Для каждой идеи из этого документа:

1. **GitHub Issue** — описание задачи, acceptance criteria
2. **Ветка** `feat/xxx` или `fix/xxx` — от main
3. **Реализация** — коммиты в ветку
4. **MR (Pull Request)** — открыть PR в GitHub
5. **CI** — дождаться зелёной сборки (build + test + lint)
6. **Ревью** — проверить, обсудить
7. **Мерж** — после одобрения пользователем

**Не мержим без:** зелёного CI + ревью.

## 📱 Удобство пользователя

### 1. Экспорт / импорт настроек (JSON backup)
**Сложность:** 1–2 дня

Экспорт всех настроек (токены, каналы, прокси, фильтры) в JSON-файл в `Download/`. Импорт из файла. Секреты (токены бота, пароли прокси) не экспортируются — при импорте на другое устройство их нужно ввести заново.

**Зачем:** смена устройства, бэкап перед обновлением, восстановление после сброса.

**Детали:**
- Файл: `sms-forwarder-backup-YYYY-MM-DD.json`
- Импорт с подтверждением (перезаписать текущие настройки?)

---

### 2. Шаблоны сообщений
**Сложность:** 1–2 дня

Пользователь задаёт шаблон для форматирования пересылаемого сообщения.

**Дефолт:**
```
📨 {sender}: {text}
⏰ {time}
```

**Переменные:** `{sender}`, `{text}`, `{time}`, `{date}`, `{type}` (sms/missed), `{number}`, `{event_number}`

**Зачем:** кастомизация уведомлений, интеграция с другими ботами (formatted output), JSON-шаблоны для автоматизации.

---

### 3. Тихие часы / расписание
**Сложность:** 2–3 дня

Не пересылать сообщения в заданное время (но сохранять в очереди — отправить потом).

**Детали:**
- Интервал: например, 23:00–07:00
- Опция: «accumulate» (копить и отправить утром) или «discard» (отбросить)
- Переключатель в UI (toggle + time picker)

---

### 4. Фильтры по отправителю / ключевым словам
**Сложность:** 3–5 дней

Условная пересылка: только от определённых отправителей или с определёнными словами.

**Детали:**
- Правила: `{sender} == "Bank" → forward`, `{text} contains "password" → forward`
- Whitelist / blacklist режим
- Regex-поддержка (с защитой от ReDoS)
- Направление: каждое правило → свой chat/channel

---

### 5. История событий (Room DB)
**Сложность:** 3–5 дней

Сейчас — последние 10 событий в памяти, теряются при убийстве сервиса.

**Решение:** Room database для хранения истории.

**Схема:**
```kotlin
@Entity(tableName = "events")
data class EventEntity(
    @PrimaryKey(autoGenerate = true) val id: Long,
    val sender: String,
    val body: String,
    val timestamp: Long,
    val type: String,          // "sms" | "missed_call"
    val status: String,        // "sent" | "failed" | "queued"
    val channelName: String?,
    val attempts: Int
)
```

**UI:** отдельный таб «История» (список с пагинацией, поиск, фильтр по типу/дате).

**Сложность:** 2–3 дня

AppWidget для быстрого включения/выключения сервиса + статус (сколько переслано сегодня).

**Сложность:** 1 день

Разные звуки / вибрация для разных типов событий (СМС vs пропущенный вызов).

### 14. Умный приоритет каналов (promote-on-success)
**Сложность:** 1–2 дня

**Проблема:** Канал «без прокси» (direct) всегда первый и не может быть перемещён вручную. При смене условий (прокси снова работает / падает) приходится менять порядок вручную.

**Решение:**
1. **Direct-канал всегда первый** — в UI он зафиксирован (иконка 🔒), его нельзя перемещать/отключать
2. **Promote-on-success** — после успешной отправки через прокси-канал, он автоматически перемещается на первое место (перед direct)
3. **Automatic fallback** — если прокси падает, direct остаётся надёжным fallback

**Зачем:**
- Не нужно вручную менять порядок каналов при смене условий
- Прокси автоматически становится primary, если работает стабильно
- Direct — всегда надёжный fallback

**Детали:**
- `ChannelStore.promote(channelId)` — перемещает канал на позицию 0 (после fixed direct)
- В UI: прямой канал показывается с иконкой 🔒 (нельзя перетаскивать)
- После promote: анимация «перелёт» вверх в списке

## 🏗️ Архитектурные решения

### 8. Dependency Injection (Hilt)
**Сложность:** 2–3 дня

Сейчас зависимости создаются вручную (new, синглтоны). Hilt даст:
- Тестируемость (мокаем зависимости)
- Жизненный цикл (scoped к Activity/Service)
- Чистоту кода (убирает передачу контекста/prefs везде)

---

### 9. ViewModel + StateFlow (MVVM)
**Сложность:** 3–5 дней

Сейчас UI логика прямо в `MainActivity`. Вынести в ViewModel:

```
MainActivity → observes → MainViewModel → uses → Repository → uses → Prefs/DB/Service
```

**Зачем:**
- Конфигурационные изменения (поворот экрана) не теряют состояние
- Тестируемость UI-логики
- Чистое разделение UI ↔ бизнес-логика

---

### 10. DataStore вместо SharedPreferences
**Сложность:** 1–2 дня

Migration `Prefs.kt` с `SharedPreferences` / `EncryptedSharedPreferences` на `Jetpack DataStore`:
- Type-safe (protobuf или preferences)
- Coroutines-first (нет блокирующих reads)
- Migration утилита для существующих пользователей

---

### 11. WorkManager для фоновой работы
**Сложность:** 3–5 дней

Сейчас `ForwardService` — foreground service. WorkManager даст:
- Guaranteed execution (даже после reboot)
- Battery-friendly scheduling
- Retry с backoff на уровне системы
- Замена foreground service (или как fallback)

---

### 12. F-Droid build variant
**Сложность:** 1–2 дня

Отдельный build flavor без:
- GitHub update checks (нет сетевых звонков к GitHub)
- Google Play Services зависимостей
- аналитики/crash reporting

---

### 13. Структурированное логирование (Timber)
**Сложность:** 1 день

Заменить `Log.d/i/e` на Timber:
- Debug build: лог в logcat
- Release: лог в файл (для debugging)
- Теги: по классам (`ForwardService`, `ChannelSender`, etc.)
